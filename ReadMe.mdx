# Agent Company

An AI software-development company made of specialized agents that share one
project context and are coordinated by a General Manager. You give it a goal;
the agents research, plan, build, test and review in a loop until the goal
passes the quality gate, and they learn from every attempt.

Guiding principle: what matters most is not how many agents you run. It's
combining capable models, specialized roles, shared project context, reliable
tools, and a controlled orchestration system.

## What it does

1. **Goal**: you enter a goal (dashboard, API or CLI), optionally with URLs to
   research, an existing git repository and quality commands such as `uv run pytest -q`.
2. **Research**: the research room crawls the URLs (following their links),
   files the pages as knowledge and summarises what is relevant.
3. **Plan**: the General Manager splits the goal into task contracts: role,
   skills, dependencies, priority and acceptance conditions.
4. **Staff**: each task gets the best idle agent of that role. A busy agent is
   cloned; a role nobody has is recruited as a new specialist and linked to the
   most similar agents so it starts from their experience.
5. **Execute**: the scheduler runs the task graph in parallel where it can, in
   an isolated git worktree on its own branch.
6. **Quality gate**: every contract is checked, reviewer verdicts are read and the
   quality commands run in the worktree.
7. **Loop**: if the gate fails, the findings go back to research and planning,
   and the next iteration starts (up to `MAX_ITERATIONS`).
8. **Learn**: every participating agent gets a lesson, XP and skill growth, and
   its playbook is updated. Collaborators are linked, and related agents see each
   other's lessons.
9. **Approve**: passing work waits for an administrator, then the branch is merged
   locally. Nothing is pushed or deployed.

## Setup

Requirements: Python 3.12+, [uv](https://docs.astral.sh/uv/) and git.

```bash
uv sync                 # installs dependencies into .venv
cp .env.example .env    # set MODEL and the keys you have; everything is optional
uv run pytest -q        # runs offline
```

## Run

```bash
uv run python -m agent_company supervise    # recommended: dashboard on http://127.0.0.1:4900, safe restarts
uv run python -m agent_company serve        # the same server without the supervisor
uv run python -m agent_company goal "Build a REST API for a todo list with FastAPI" \
    --check "uv run pytest -q" --url https://fastapi.tiangolo.com/tutorial/
uv run python -m agent_company approve 1    # merge goal 1 after review
uv run python -m agent_company models       # what each role would use right now
uv run python -m agent_company agents       # agents by room
uv run python -m agent_company crawl https://docs.crewai.com/ --depth 1
uv run python -m agent_company eval --suite smoke --label v1 --repeats 3   # benchmark the company
uv run python -m agent_company learn gaps|raise|plans|plan <agent> <skill>|start <id>|experiments|metrics
uv run python -m agent_company goal "Fix the bug" --repo ~/proj --allow 'src/*' --protect-tests
uv run python -m agent_company "Build a REST API for a todo list"   # classic crew -> output/
```

Without any key, goals run on the offline simulator: the whole loop runs
(planning, staffing, worktree, gate, learning, approval) with placeholder content.
Set `EXECUTOR=offline` to force that, for example in tests.

Approving a goal merges its branch into the repository's current branch, which must
have no uncommitted changes to tracked files. For the protected platform project
that is this checkout: commit your own work first, or approval is refused.

A goal without `--repo` gets a fresh git workspace in `data/workspaces/`. With
`--repo`, the agents work in a worktree of that repository on branch
`agents/goal-<id>`, and approval merges that branch into the branch it started
from (the repository must be on that branch, with no uncommitted changes).

Known limits: the worktree and branch stay in place after approval (remove them
with `git worktree remove` when you no longer need them). A goal interrupted by a
restart resumes at the iteration it was on, but without the previous gate's
findings.

## Projects and the command window

**Projects** (admins create them) are git repositories the company works on: a
work folder (an existing folder becomes a repository; empty means a fresh
workspace), a GitHub URL and default quality commands. The page lists projects
on the left (check boxes or Ctrl+click select several for deletion), the command
window of the selected project in the middle, and the agents working on it on
the right (click one for its card).

The command window is a conversation with the project's General Manager. A plain
order becomes a goal for that project; the GM posts the plan, each task's result,
proposals and the gate result back into the thread. Attach files with **Attach**
or by pasting an image; agents find them in `.attachments/` in their worktree
(never committed). Claude Code and Codex can open them there; API models only see
the file names (images are not sent as image content). Every message has a copy button, and identical consecutive
messages collapse into one with a count. Slash commands:

| Command | Does |
| --- | --- |
| `/standup` | Every agent on the project reports what it is doing and what it last finished |
| `/status` | The project's recent goals and their state |
| `/stop` | Cancels the project's running and queued goals |
| `/sync` | Pushes approved work to the GitHub remote (administrators) |
| `/help` | Lists the commands |

This repository is registered as the protected **Agent Company** project: it
cannot be deleted or renamed and only administrators see it, so agents can work
on the platform itself. Approved changes are merged into this checkout; restart
the service to load them.

### Proposals

Agents may end a task with `PROPOSAL: <title> :: <why>`. By default proposals
wait for an administrator (Projects page, or `POST /api/proposals/<id>/approve`);
with the setting `proposal_policy = superiors` the General Manager decides them.
An approved proposal becomes a new goal in the same project. One goal and its
descendants may spawn at most `max_proposal_goals` goals, so agents cannot keep
creating work for themselves.

### Pushing to GitHub

Approval merges a goal's branch locally. `/sync` (or **Sync to GitHub**) then
pushes that branch to the project's GitHub URL; with `AUTO_PUSH=1` this happens
after every approval. Only commits that came from approved work are pushed: the
checkout's own uncommitted changes are never staged. Missing entries of a
source-only `.gitignore` (`node_modules/`, `.venv/`, `.env`, `data/`, ...) are
added in a commit of their own, and commits with files over 50 MB are refused.
Credentials come from `gh auth` when it is logged in, otherwise from git's own
configuration. Administrators can give each user a Git name, email and branch
(`PUT /api/users/<id>/git`); that user's work is committed and pushed under it.

## What the quality gate checks

Besides each task's contract and the reviewer's verdict, every iteration's change is checked for:

| Check | Fails when |
| --- | --- |
| Secret scan | An added line holds something that looks like a credential: private keys, Anthropic/OpenAI/OpenRouter/GitHub/Slack/Google/Stripe/AWS keys, or a hard-coded password or token (obvious placeholders are ignored) |
| Syntax | A changed Python, JSON, TOML or shell file does not parse; JavaScript, Ruby, PHP and Go too when `node`, `ruby`, `php` or `gofmt` is installed |
| Scope | A changed file is outside the goal's allowed paths (`--allow 'src/*'`), or an existing test was changed or deleted while tests are protected (`--protect-tests`); new tests are always allowed |
| Commands | A quality command exits non-zero |

Quality commands are first run on the **untouched code**. A command that already
failed there is reported as pre-existing ("the goal may be to fix it"), and with
`allow_preexisting_failures` it does not block the gate. An administrator's goal
that sets no quality commands uses the test and lint commands its description
names in backticks or a shell block (for example "check with `uv run pytest -q`").

Each iteration gets a score (the share of checks that passed). If the last
iteration fails and scored worse than an earlier one, the goal's branch is reset
to the best iteration, so a late regression doesn't throw away better work.

Budgets (Settings): `goal_budget_usd` caps the model spend per goal and
`goal_time_budget` its wall-clock time. At 60% the agents are told to converge;
at 100% the goal stops (and keeps its best iteration).

## Organisation

Every room in the design exists, and each role has one seeded agent:

| Division | Rooms |
| --- | --- |
| Management | Company General Manager, Administrative Management Room, Agent Management Room |
| Development | Development Flow (Architect, Backend Developer, QA, Frontend, DevOps) |
| Research | Information Collection Room, External Data Room (rotational), Analysis Room, Comprehensive Analysis Room |
| Learning | New Technology Lab, New Technology Introduction Room, Study Room, New Technology Classroom |
| Business | Product Introduction Room, Sales Room |
| Security | Security Room, Network Security Room, Security Guard |

The core pipeline (General Manager, Architect, Developer, QA) and the research
rooms are enabled. The other roles are registered but disabled until the pipeline
is reliable; enable them on the Agents page. A plan that asks for a disabled role
gets the Developer (for write tasks) or QA (for read tasks) instead. Every agent
reports to a superior (the General Manager at the top). Agent names cannot be edited.

## Which agent uses which model

The defaults put strong models on planning and design, a coding agent on code, a
mid-tier model on review and cheap or free models on bulk reading. Change any
route on the Models page.

| Role | Default route | Why |
| --- | --- | --- |
| General Manager, Architect | Claude Opus 5.5 | Planning and design decide everything downstream |
| Developer, Frontend, DevOps, Lab | Claude Code | Real file and tool access in the worktree |
| QA, Security, Analysts | Claude Sonnet 5.5 | Careful review at a lower price |
| Research Lead, others | Claude Haiku 5.5 | High-volume summarising |
| External Data, Study Room | OpenRouter Free router | Bulk collection at no token cost |

For each agent the router tries, in order: the agent's own model preference, then
its role's route, then `MODEL` from `.env`. It skips any model whose key or CLI is
missing, that is disabled, or that has reached its daily or weekly token limit, and
it records why. Only when none of them is usable does the offline simulator stand
in, so the whole loop still runs on a machine with no model configured; once a real
model is in use, its failures are real failures and are never papered over by
simulated work.

### Claude Code

Claude Code writes the code. With `ENABLE_CLAUDE_CODE=1`, Developer tasks run
`claude -p` inside the goal's worktree. Claude Code may read, edit and write files
there, and through Bash it may only run tests and `git status`/`git diff`. It uses
your `claude` login (Claude subscription), or `ANTHROPIC_API_KEY` when that is set.
The run's tokens and cost are recorded. You can also keep working in VS Code with
Claude Code on this repository as usual; `CLAUDE.md` tells it the conventions.

### OpenRouter

Models page → **OpenRouter models**: search OpenRouter's public catalog (free
models first, with prices per 1M tokens and context size) and add one with a
click. Any model id can also be added by hand as `openrouter/<vendor>/<model>`.
OpenRouter models need `OPENROUTER_API_KEY`. A key without credits can use the
free (`:free`) models, which have daily request limits.

### Asking ChatGPT from an agent

A ChatGPT subscription covers the ChatGPT app, not programmatic use. An agent that
calls OpenAI models uses the OpenAI API (`OPENAI_API_KEY`, model id `openai/<model>`),
which is billed per token. Free options are OpenRouter's free models and local
models through Ollama (`ollama/<model>` plus `OLLAMA_API_BASE`). The Codex CLI
(`ENABLE_CODEX=1`) can use an eligible ChatGPT plan, subject to that plan's limits.

## Model fallback, retries and local servers

- **Fallback:** if a model call fails (rate limit, overload, network), the same
  request goes to the next usable real model in the role's chain (agent
  preference, route, `MODEL`). If all of them fail, the task fails; the simulator
  never substitutes for a real model that failed.
- **Retry model:** each route can name a stronger model for iterations after a
  failed gate (by default QA, Security and Analyst retry on Claude Opus 5.5, and
  Research on Claude Sonnet 5.5).
- **Different reviewer family:** QA and security reviews prefer an available model
  from a different provider than the one that wrote the code, so the reviewer
  isn't blind to the same mistakes.
- **Local servers:** add a model with a base URL of an OpenAI-compatible server
  (llama-server, LM Studio, vLLM) and the model id `openai/<name>`; for example the
  Qwen3-Coder llama-server in `/home/thomas/bit/local-llm/serve.sh` is
  `http://172.17.0.1:18100/v1` with id `openai/local/qwen3-coder-30b`. An optional
  `api_key_env` names the variable that holds its key.
- **Test:** the Models page's **Test** button sends a one-word prompt and shows the
  reply, tokens and time.

## More models

- **Model catalogs** (Models page): besides OpenRouter, search the chat models of
  Groq, Mistral, Cohere and SambaNova (their OpenAI-compatible model lists) and add
  one with a click. They need `GROQ_API_KEY`, `MISTRAL_API_KEY`, `COHERE_API_KEY` or
  `SAMBANOVA_API_KEY`.
- **Claude Code sessions:** an agent's next task on the same goal within 60 minutes
  resumes its previous Claude Code session (`--resume`), so a retry does not re-read
  the code from scratch.

## How agents evolve

- **Versioned playbooks:** every few new lessons, an agent's playbook is rebuilt
  from its recent lessons (`DO:` rules from passed work, `AVOID:` warnings from
  failures) as a new version. Every version is kept; administrators can restore
  any of them from the agent's card.
- **Experiments:** when an agent's last outcomes pass the gate less than half the
  time, it gets a failure-aware candidate playbook (warnings first) instead of a
  direct change. The candidate first runs the smoke suite against the current
  playbook (same suite, same repeats, sample sizes kept), then has a canary of 3
  live tasks; it is promoted only if it beats the old success rate by
  `min_improvement` points and rolled back as soon as the canary can no longer get
  there. The agent is then not re-diagnosed until it has 6 new outcomes. Every
  candidate is an experiment record (Evolution → Experiments); administrators can
  propose their own: a playbook for one agent, or another model for a role's route.
  A better route is only recommended: an administrator applies it, and its canary
  restores the old route if live work gets worse. Governance, security,
  permissions, budgets and approvals are never experiment targets.
- **Capability gaps and learning plans:** per agent and skill, readiness comes from
  verified knowledge, gate outcomes of tasks with that skill, eval runs and recency.
  Gaps (missing capability, insufficient proficiency, outdated, poor performance:
  3 of the last 4 tasks on a skill failed, low reliability) are raised by the
  evolution cycle, and where an eval suite covers the skill a learning plan is
  proposed: knowledge to study, practice exercises (`evals/*-practice.json`) and a
  separate final evaluation (`evals/*-final.json`) whose checks the agents never
  see. Both run as eval goals in scratch repositories with the trainee doing its
  role's work; only the final evaluation's result changes the certified level of
  the skill, and a failed one recommends retraining. Plans are started by a person
  (`learn start <id>` or Evolution → Learning plans).
- **Clones:** when every agent of a role is busy, the best one is cloned. After the
  goal, idle clones merge their XP, skills, task counts and lessons back into the
  original and retire. **Merge idle clones** on the Evolution page does the same
  for a whole role.
- **Team compatibility and fair staffing:** staffing scores candidates by skill
  coverage, level, how well they have worked with the agents already on the goal,
  and quality (the success rate over their last 20 verified task outcomes, so old
  failures fade), minus the goals they are already working on. An agent with fewer
  than 3 outcomes gets the pool's average quality: no bonus, no penalty. Now and
  then (`explore_rate`, default 10 %) a non-critical task of a user's goal goes to
  such a new agent so it can build a record. Each task keeps its staffing decision
  with every candidate's score.
- **Relationships:** agents are linked by kind, each with the evidence that made
  it: `similar` and `complementary_skill` (inferred from profiles), `collaborated`
  (only goals that passed the gate), `reviewed_by`, `depends_on`, `handover_to`,
  `research_partner` and `knowledge_contributor` (observed in finished work), and
  `mentored_by`. Each piece of evidence counts once. A new agent is linked to
  similar agents, to the specialists of other roles its peers work with, and to a
  mentor candidate (the most certified agent of its role). Administrators can
  correct a link's weight or expire it, with a reason, on the agent card's
  Relationships tab (audited). The **Agent network** page shows the whole network:
  counts (active agents and links, current teams, certified capabilities, recent
  handovers, mentorings, agents with no free slot) and a graph of the links,
  filtered on the server by agent, room, skill, kind and origin, one page of 100
  links at a time and at most two steps around a chosen agent. Line style and colour
  show where a link came from (observed, inferred, corrected), width its weight, an
  arrow a directed kind; the table under the graph lists the same page with evidence.
- **Mentoring:** a learning plan gets a mentor when the learner has one. The mentor
  reads the practice results and writes advice (what to study, what to practise);
  people can add advice too. It never grades: only the final evaluation certifies.
- **Handovers:** when a task is retried in the next iteration, the agent gets a
  handover package (previous agent, status, files changed, known problems, commit,
  next actions); a handover between two different agents is recorded on both cards.
- **Lifecycle:** agents are active, paused or retired. Retirement is permanent and
  keeps the agent's history; names never change. Administrators can create agents
  for new roles and clone, pause, resume or retire existing ones.

## Measuring the company

- **Eval harness:** `uv run python -m agent_company eval --suite smoke --label sonnet-v1 --repeats 3`
  runs every task of `evals/smoke.json` three times, each in a fresh repository,
  and reports per task how many runs passed, why runs ended, iterations, time and
  cost. A task counts as solved only if every run passes. Change a route or a
  model, run again under a new label, and compare with
  `eval --compare sonnet-v1 opus-v1` (or on the Performance page). A suite is a JSON
  file of tasks with seed files and check commands; eval goals never merge, push
  or notify. The offline simulator solves none of the bundled tasks, on purpose:
  they need real code.
- **Defects:** every failed gate check becomes a defect of its goal (critical:
  credentials or a refused command; high: failing command or syntax; medium:
  scope or reviewer FAIL; low: a task contract). It closes when a later iteration
  passes that check and reopens if it fails again. Administrators can accept the
  risk or defer it.
- **Model benchmarks:** `eval --suite smoke --model <catalog name> --role developer`
  runs the suite with that model standing in for the role (label `model:<name>`);
  routes change only by an administrator.
- **Certification:** each agent has a level L0-L5 for its role, computed from its
  gate outcomes and eval runs. L3 needs at least 3 passes in 5 outcomes, L4 at
  least 10 passes at 75% across 2 goals, and L5 at least 25 passes at 85% across 5
  goals including 5 eval passes, so one hard task never makes an expert. A level
  drops by one when the newest evidence is more than 90 days old. Per skill, the
  level certified by a learning plan's final evaluation is listed as well.
- **Performance:** per agent: completion, rework (tasks redone in a later
  iteration), reliability (model calls that succeeded), average task time,
  tokens, cost, collaborators and the pass rate of its goals; the same per room;
  and for the company: pass rate, iterations to pass, cost per passed goal and
  open defects. Learning metrics (`/api/learning/metrics`): first-pass success
  rate, rework frequency, knowledge reuse (retrieved items that went into passing
  goals) and the benchmark result of each playbook candidate.

## Research

**Research** page → **Collect a website**: give a URL and a link depth. Depth 0
fetches only that page; depth 1 also fetches every page it links to on the same
site; depth 2 goes one level further (at most 200 pages per run). The crawler obeys
robots.txt, reads only HTML and text, and refuses private or loopback addresses
unless `ALLOW_PRIVATE_CRAWL=1`. Collected pages are searchable and are given to the
agents working on matching goals.

The External Data Room works **in rotation**. Add sources on the Research page;
each visit (`ROTATION_INTERVAL` seconds, or **Run next**) assigns the next due
source to the agent on duty, so the work and the experience are spread across the
room. The rotation is worked in **shifts** that cycle acquisition → verification →
analysis → organisation → review (`shift_seconds` in Settings; 0 makes every visit a
shift of its own). A shift records the sources it read and when, its findings, pages
it could not verify, failed visits and the open questions they raise. When it ends,
the next agent on the roster gets a handover package with all of that plus the
waiting research requests, outstanding sources and next actions. If the agent on duty
is paused, disabled or retired, or an administrator presses **Replace agent**, the
next agent continues the same shift without losing its findings or open questions.
The agent card shows each agent's open tasks, hours active in the last 24 hours and
its last handover.

The learning pipeline: new information (crawl) → research (summaries) → knowledge
(documents) → experiments (goal iterations) → evaluation (quality gate) → improved
agents (lessons and playbooks).

## Knowledge safety

Collected pages keep their provenance (URL, when, which agent) and are labelled by
the kind of source: standard, academic, source repository, package registry,
official documentation, community Q&A, blog or other web page. Different kinds
deserve different weight, so there is no single trust score. Pages whose text tries
to instruct the reader (override earlier instructions, take on a new role, reveal a
system prompt, fake a chat turn, send credentials somewhere, run destructive
commands) are flagged; they stay in the knowledge store for people to read but are
never put into an agent's prompt. Everything else reaches agents wrapped in
`<document>` tags with its kind and date, and agents are told it is data, not
instructions.

**Ask the research room** (Research page or `POST /api/research/requests`) takes a
question and optional URLs. The research lead collects the URLs, searches the
knowledge store and writes a report with objective, numbered findings citing their
sources, gaps, a recommendation and the source list; the report is filed as
knowledge too.

## Users

The dashboard asks only for a name and has a **Register** button. The browser
creates a random device secret, kept in its storage; the server stores only its
hash. The first account becomes the administrator. Later registrations wait on the
**Users** page until an administrator approves them; the waiting screen checks
every 10 seconds and signs in automatically once approved. After that, the
registered browser signs in by itself with no password; other computers are
refused. Administrators can reject, disable, enable, reset a computer, promote or
delete accounts. Only administrators can point a goal at an existing repository
or set its quality commands, because those run commands on the server.

## The General Manager, Claude Code and the company's tools

You talk to the company through its **General Manager**. By default the GM is **Claude Code**
(see `docs/1.claude-code-multi-agent.jpg`): on the Projects page an administrator talks to it as a Claude Code
conversation in the project's folder. Its instructions give it a toolbox:

```bash
uv run python -m agent_company gm status        # agents, running goals, catalog
uv run python -m agent_company gm agents        # who exists, with skills, plugins, model
uv run python -m agent_company gm create-agent data_engineer --skills "sql=7" --plugins "code-review"
uv run python -m agent_company gm add skill kubernetes --description "…" --content "…"
uv run python -m agent_company gm configure 3   # write the catalog into project 3's .claude/
uv run python -m agent_company gm goal 3 "Add a CSV export" --check "uv run pytest -q"
uv run python -m agent_company gm study         # one learning visit (rewrites an agent's definition)
```

- **Switching the GM**: Agents → Company General Manager → Model: any model, a Claude Code at another address
  (a Claude Code model with a base URL), or another agent (it then uses that agent's model).
- **Spec-driven loop**: every goal writes `.claude/specs/<slug>/` (requirements, tasks, spec, design, review,
  sa-review, decisions) and loops Plan → Build → Review → Fix until the gate passes. A CLI GM first updates the
  project's `.claude/` (agents, rules, skills, commands, settings.json, .mcp.json) in the goal's worktree.
- **Catalog** (Agents → Skills & plugins): skills, plugins, rules, commands and hooks the agents share; the GM
  adds what is missing. **Tools & MCP** (Agents tab): MCP servers with encrypted secrets, tool allow-lists and
  per-agent grants; Claude Code agents get their granted servers.
- **Learning changes the agent itself**: each agent is a versioned definition file in `data/agents/` (its own git
  repository). The loop runs the agent from it; learning and the study rotation (`study_interval`) rewrite it.
- **Hooks** (fail-open): TaskCreated, TaskCompleted, TeammateIdle are appended to `data/logs/team-hooks.jsonl`.
- **Emergency stop** (System): cancels running and queued goals and refuses agent runs until lifted.

| Run | on | Giving orders, starting goals and asking the research room; without it the user only reads |
| Create projects | off | Creating projects in a new workspace (choosing a folder or quality commands stays admin-only); the creator is granted the project |
| Manage agents | off | Creating, cloning, pausing, retiring and editing agents; evolution actions |
| Manage models | off | Adding, editing, testing and deleting models; changing routes |

Always admin-only: users, files, settings, audit log, system, pushing to GitHub and
approving work. The protected platform project is never visible to a non-admin.
Each user can also have a Git name, email and branch (Users page → **Git**): goals
they order are committed and merged under that identity and pushed to that branch.

## Administration

- **Settings** (admins): the values in `.env` can be overridden here and apply at
  once (iterations, parallelism, approval, proposal policy, budgets, auto-push,
  default quality commands, executor). **Reset** returns to the `.env` value.
- **Notifications**: goals waiting for approval, failed goals, proposals and new
  registrations; the bell shows the unread count. Administrators can post a notice
  to every user. The browser tab icon shows how many goals are running (blue) or
  waiting for approval (amber).
- **Audit log** (admins): every administrative action (users, settings, models,
  routes, agents, approvals, projects, pushes) and every refused command, with
  actor, before/after values and time. Records are hash-chained; the page shows
  whether the chain is intact, so an edited or deleted record is detected.
- **Security** (admins): the active stop level and stops, security incidents (open
  first, worst first; containment and status steps), refused commands per agent and
  the latest ones, and security alerts. Every user sees an active stop level (for
  example `E1 stop`) in the top bar, without its scope.
- **Knowledge** (admins): what agents learned, with the goal, task and commit each
  lesson came from. Search, approve or reject, write a new version, or delete an
  item. Lessons that contradict each other appear side by side; you decide which
  holds (or both) and give a reason, and until then both rank lower in prompts.
  The graph button (or a `type:id` such as `agent:3`, `goal:12`, `skill:testing`)
  opens the knowledge graph around it: who created an item, what it applies to,
  which goals used it, which tasks an agent was assigned, what supports a
  decision. Click a node to centre on it.
- **Goal trace**: the clock button on a goal shows every run, gate result,
  decision and operation on one time line, with totals per agent and model.
- **Command policy**: quality commands, project commands and check commands are
  refused before they run when they would escalate privileges (`sudo`), delete
  root/home/parent paths, wipe disks, deploy or push, drop databases, change
  firewalls or accounts, pipe a download into a shell, stop services or tamper
  with audit history. Refusals are audited as high severity.

## Platform

- **Files** (admins): browse the project folders and `data/` in one or more panes
  (**+ Pane**, close with ✕). Ctrl/Shift+click selects several items; drag them
  onto a folder to move them; copy, cut, paste, rename, delete and upload work on
  the selection. Double-click opens a file: code is shown with syntax colours,
  Markdown rendered (with a Source toggle), and **Edit** saves changes. Nothing
  outside the project folders can be read or changed, `.git` is read-only, and
  every write is in the audit log. **Browse…** in the new-project form picks the
  work folder.
- **Safe restart:** run the service as `uv run python -m agent_company supervise`.
  When the code under `src/` changes (for example after approving a goal of the
  protected platform project), the supervisor syntax-checks it, boots a candidate
  on port + 1 without background work, health-checks it, waits until no goal is
  running and then swaps the server. A candidate that fails never replaces the
  running service; the reason is shown on the **System** page, which also has a
  **Restart safely** button and shows host load, memory, disk, the service process,
  running work and the repository's uncommitted changes. A crashed server is
  restarted with backoff. The dashboard itself is served from disk and needs no
  restart.
- **Live updates:** the dashboard listens to `/api/stream` (Server-Sent Events) and
  refreshes when something changes; it falls back to polling every 5 seconds.
- **Screen formats:** the columns button in the top bar picks one of 21 formats
  (Standard, Compact, Comfortable, Focus, Zen, Wide chat, Agent ops, Mirror, Command
  centre, Stacked, Presentation, Large text, Dense data, Ultrawide, Laptop, Tablet,
  Mobile, Cinema, Floating cards, Labelled rail, Square). Each sets scale, density,
  corners, where the navigation rail sits (left, right or bottom, with or without
  labels), the page width and how the Projects page arranges its three panels.
  Drag the gutters between those panels to resize them; widths are remembered per
  format in this browser. Light and dark theme are separate (moon/sun button).

## Technology choices

| Layer | Choice | Why |
| --- | --- | --- |
| Language | Python 3.12+ with `uv` | One language for agents, orchestration and API; CrewAI is Python |
| Agent models | CrewAI `LLM` | One interface to Anthropic, OpenAI, OpenRouter, Ollama and others |
| Coding agents | Claude Code CLI, Codex CLI | Real file and tool access inside a worktree |
| API | FastAPI + Uvicorn | Typed, fast, small |
| Database | SQLite by default; PostgreSQL via `DATABASE_URL` | Zero setup to start; same schema on PostgreSQL |
| Queue | In-process scheduler persisted in the DB | Enough for one machine; Redis + BullMQ when it runs on several |
| Dashboard | Static HTML/CSS/JS served by the API | No build step; light and dark themes |
| Tests | pytest | Every test runs offline with its own database |

The design's suggested Node.js / Next.js / Redis stack is what
`/home/luca/AgentForge` already uses for its website. This repository is the
Python agent engine, so it stays with the stack CrewAI needs and adds Redis or a
Next.js front end only when one machine is no longer enough.

## Safety

- Agents never edit the main checkout. File-changing executors run only inside
  `data/worktrees/`, and file blocks that point outside the worktree are refused.
- Claude Code's Bash access is limited to tests and read-only git; Codex runs in its
  `workspace-write` sandbox. This is not a container: for untrusted goals, run the
  service in a disposable VM or container with no production credentials.
  Administrators can install Docker and launch LXD VMs from System view (or
  `python -m agent_company host ...`), and run Linux and Windows VMs with an in-browser
  console from the Machines view; agents cannot reach these controls.
- Nothing is deployed. Merging is local and needs approval (`REQUIRE_APPROVAL=1`,
  the default); pushing to GitHub happens only on `/sync` or with `AUTO_PUSH=1`.
- Commands that would deploy, push, escalate privileges, delete root or home paths,
  drop databases or change firewalls are refused before they run (and audited);
  changes that add credentials fail the gate.
- Web pages, repository files and tool output are passed to agents as untrusted
  data; pages that try to instruct agents are kept out of prompts, and the crawler
  refuses private network addresses (also after redirects).
- Administrative actions are recorded in a hash-chained audit log.
